# 読む前に構造が分かる資料

提案資料・説明スライドの構成とレイアウトを決めるときに使う。少数色・余白・整列を維持しながら、意味のある枠・図形・画像・表を積極的に使う。ユーザーの既存テンプレートと明示指定を優先する。

## 比較から得た知見

「ラスワンのお気持ち顧問」の文字中心版と図解改訂版（各10枚）を比較した。ユーザーは図解改訂版を高く評価した。以下の効果は資料の構成と表示からの分析であり、読解速度の実測結果ではない。

両版とも色・余白・文章の短文化を使っていた。主な改善は情報量の追加ではなく、文章の関係を視覚的に示した点にある。

| 対象 | 文字中心版 | 図解改訂版での修正 | 読者にとっての違い |
|---|---|---|---|
| 2ページ：課題 | 2列の見出しと本文 | 営業とAIの課題を別枠で囲み、見出し帯と結論帯を配置 | どこまでが同じ話か、共通する要点は何かを識別しやすい |
| 3ページ：支援内容 | 2つの支援を文章で並列紹介 | 支援ごとの枠と接続矢印、共通の改善方針を配置 | リスト戦略とAIコールのつながりを理解しやすい |
| 4ページ：AIコール | 業務設計・接続・改善の説明行 | 設計、接続、架電・回収、改善の4工程に再編集 | 何をどの順に進めるかを追いやすい |
| 5ページ：リスト戦略 | 項目名と説明を縦に列挙 | 「支援の段階／実施すること／営業現場での使い方」の表 | 活動と利用目的を同じ行で照合できる |
| 6ページ：相談領域 | 営業と経営を2列で紹介 | 相談者と4つの支援領域を別のまとまりで表示 | 誰の、どの課題に対応するかを把握しやすい |
| 7ページ：進め方 | 数字と説明を横に配置 | 各工程を枠で囲み、矢印で接続。確認指標を別帯へ | 順序と、工程をまたいで確認する項目を区別できる |
| 8ページ：人物紹介 | 写真と経歴の文章 | 写真を維持し、経歴をラベル付きの行に整理 | 営業・創業経営・現在の活動の位置づけが明確 |
| 9ページ：料金 | 価格、支援方針、条件を離して配置 | 価格を強調面に集約し、支援と契約条件を表に整理 | 価格と検討条件を同時に把握しやすい |
| 10ページ：相談 | 説明文とQRコード | 相談手順を番号付きの枠に、QRと案内を同じ白地へ | 次の行動と連絡先を見つけやすい |

実ファイルでは文字中心版のネイティブ表・コネクタは各0、改訂版は表2個、コネクタ9個。画像は両版とも人物写真とQRの2個で、画像の追加が改善の主因ではない。改訂版のフローは通常の図形とコネクタで、ネイティブSmartArtではない。数値グラフは両版ともない。個数を品質目標として使わない。

## 表現を選ぶ判断基準

最初に「並列」「順序」「対応・比較」「全体と部分」「数量」「実物」のどれを伝えるかを決める。

| 伝えたい内容 | 適した表現 | 使う条件・注意 |
|---|---|---|
| 独立した課題、サービス、対象者 | 枠・背景面によるグループ | 見出しと説明を一緒に囲む。1文ずつ別枠に分解しない |
| 工程、導入、相談手順 | 番号付きフロー、適切なSmartArt | 実際に順序がある場合。通常は左から右、上から下 |
| 項目ごとの内容と条件、比較 | ネイティブ表 | 各行を共通の列見出しで比較できる場合。長文を押し込まない |
| 支援同士の連携、親子関係 | 関係図、階層図 | 接続の意味を説明できる場合。必要なら矢印に短いラベル |
| 人物、製品、画面、現場 | 出典のある写真・スクリーンショット | 実物を知る意味がある場合。画像内の根拠を隠さない |
| 数量比較、時系列、構成比 | 適したネイティブグラフ | 比較可能な実データがある場合。数字・単位・期間を保持 |
| 単一の主張、短い説明 | タイトルと本文 | 図形が理解を助けない場合は簡潔な文字組みを使う |

「必要に応じて必ず入れる」は、理解に必要な表現を省かないという意味。画像・SmartArt・グラフ・表を全種類入れる義務にはしない。年額1つだけなら価格の強調でよい。実績や改善率がなければグラフ用の数値を捏造しない。

## 枠と図形の設計

- 枠の役割を決める。「1つの課題」「1つの工程」「1つの料金プラン」など意味単位にする。
- 同じ階層は同じ幅、高さ、内側余白、見出し位置を基本とする。文字量の違いはまず短文化で整える。
- 色の役割を固定する。例：白地は個別説明、濃色面は共通の要点、強調色は工程番号や重要条件。すべてを強調しない。
- 共通の結論は複数枠の下などにまとめる。毎ページの帯を義務化せず、タイトルの繰り返しになる帯は省く。
- 余白は情報の区切りとして残す。空いている場所を埋めるためにアイコンや枠を足さない。
- 写真とキャプション、QRと行動案内は近づけ、どの説明に対応するかを明確にする。

## 図解で意味を変えない

矢印は装飾ではなく関係の主張になる。並列のサービスを縦に並べた表紙などで、単に見栄えのために矢印を入れると、存在しない順序や依存関係を示してしまう。並列なら矢印なし、共通の土台なら包含や共通ラベルを選ぶ。今回の改訂版も全配置をそのまま模倣する完成テンプレートとして扱わない。

工程図へ再編集するときは、原資料にある作業の順序を確かめる。提案として追加した工程・指標は「案」「例」と表示する。工程の分割とサービスの追加を混同しない。

線を減らし、直交する接続を優先する。意味のない斜線や交差を避ける。コネクタのAPIで指定した始点・終点・矢印端が見た目と一致するとは限らないので、レンダリング後に矢印方向を確認する。

## PowerPointの編集性

- 図解は通常図形とコネクタ、表はネイティブ表、データグラフはネイティブグラフを使う。スライド全体を1枚の画像にしない。
- SmartArtは工程や階層に適合し、作成環境が対応する場合に選ぶ。未対応なら編集可能な図形で表現し、SmartArtとして納品したとは言わない。
- 枠で情報をまとめることは「視覚的なグループ化」。PowerPointのグループ操作は別。利用するAPIが対応するなら、一緒に移動する枠・見出し・本文を編集上もグループ化する。未実施の場合は実施済みと説明しない。
- HTML生成器の型や個数制限はHTML実装の制約。PowerPointにそのまま押し付けず、指定形式の作成手段を使う。逆に、この参照の追加だけでHTML生成器に新しい型が増えたとは解釈しない。

## 表示と内容のチェック

1. 本文を読む前でも、どこが1つのまとまりか分かるか。
2. 枠ごとの役割、矢印の意味、表の列見出しを説明できるか。
3. 図解への変換で、存在しない因果・工程・成果を追加していないか。
4. 枠内の文字が下にはみ出していないか。句点や単語の末尾だけが次行に残っていないか。
5. 強調面が競合せず、主題と確認条件を見つけられるか。
6. 表の対応、数値・単位・期間、写真の説明が正しいか。
7. 図表が編集可能か。見た目だけでSmartArtやグループ化を実施済みと判断していないか。

全ページのレンダリングを確認し、問題があれば短文化・枠寸法・配置を修正して再確認する。自動検査の合格だけでは図解の意味と読みやすさを保証しない。
